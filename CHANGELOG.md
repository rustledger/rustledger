# Changelog

Shipped work, by area. Forward-looking plans live in [docs/roadmap/](docs/roadmap/index.md); completed items land here so the roadmaps stay forward-only.

### Breaking

- **`date_add` refuses a fractional day count instead of truncating it** — the second argument went through `Decimal::to_i64`, which truncates toward zero, so `date_add(d, 0.5)` silently added no days at all and `date_add(d, 1.9)` added one, neither of them flagged. Both now report a type error naming the rule, the same rule the new `date ± n` operator applies, and a whole-valued decimal such as `30.0` still works. **A query passing a fractional day count now errors where it previously returned a quietly wrong date.** bean-query refuses the call outright (`no function matches "date_add(date, decimal)"`), so this moves toward it (issue #2324).
- **`rustledger_loader::LoadError::Io` gained an `include_site` field** — when a read failure comes from resolving an `include`, the variant now records where that `include` was written, as an `IncludeSite { file, span, file_id }`. `LoadError` is not `#[non_exhaustive]`, so code that constructs `LoadError::Io` must set `include_site: None`, and a match that names the variant's fields without `..` must add it. `LoadError::at_include` and `LoadError::include_site` are new alongside it (PR #2322).
- **`rustledger::cmd::extract_cmd::Args` fields that had defaults are now `Option`** — `currency`, `date_column`, `date_format`, `narration_column`, `amount_column`, `delimiter` and `skip_rows` were concrete types filled from clap defaults, which made an unset flag indistinguishable from one set to its default; merging them over an `importers.toml` entry would have overwritten the entry's own values with defaults nobody typed. They are `Option` now and the default is applied where it is used. `account` made the same change in 0.24.0 (PR #2263) without an entry here. The command line is unaffected, and so are callers that parse `Args` with clap; code that constructs `Args` directly should pass `None` for a value it does not want to set (issue #2304).
- **`SourceFile::num_lines` is no longer `const fn`** — the line-start table it counts is built on first use now, behind a `OnceLock`, so the method reads a lazily-initialized value and cannot be `const`. Callers using it in a const context need to move the call; every other use is unaffected. `rustledger_booking::interpolate_in_place` and `Rollback` are new public API alongside it, for callers that want to interpolate a transaction they own rather than a copy (PR #2105).
- **`Posting::cost` and `Posting::price` are boxed** — both are now `Option<Box<CostSpec>>` / `Option<Box<PriceAnnotation>>`. `Posting` was 280 bytes and a plain two-posting expense carried roughly 190 bytes of `None`; the two largest and least often present fields are now behind a pointer, taking it to 160. This is not only a memory question: rkyv mirrors the in-memory layout, so every byte of that absent-cost padding was written to the parse cache and then validated and materialized on every cache hit, which is why the archive ran 5.2x the size of the ledger it came from. The cache file drops 36%, peak RSS 11-28% depending on shape, and warm `check` 1.8%; ledgers that *do* carry costs, where the boxes are really allocated, come out flat (-0.1% / +0.03%). Reading through the field takes `as_deref()` — `Deref` carries field accesses, so most call sites are unaffected; construction takes `Box::new` or `.map(Box::new)`. Both parse-cache versions move (loader v29, WASM v15): the archived *values* are unchanged and only the *shape* moved, which is the more dangerous kind to get wrong, because nothing downstream looks wrong while the bytes are read at the wrong offsets (PR #2104).
- **`rustledger::report::SourceCache` is removed** — it exposed `new` and `add` and no reader: the `sources` field is private and there is no getter or iterator, so nothing inside or outside the crate could read what went into it. `check` filled one on every run — a read plus a lossy UTF-8 decode per source file — and dropped it; the diagnostic paths re-read their own source at the point of use, which is why the gap went unnoticed. `Utf8Chunks::next` was the hottest single function in a `check` profile at 9.8% of all instructions, entirely for this. Embedders constructing one can delete the call (PR #2104).

- **`BookingEngine::apply_posting` is now `replay_posting`, and the realize path is private** — one public entry point served two different questions. *Realizing the booked ledger* (`apply`) treats booking's decision as authoritative, and a `{*}` meeting a pool other than the one booking recorded is a defect it refuses (#2068, #2070). *Replaying a filtered subset* — what the query executor does with whatever a `WHERE` clause left — legitimately meets a different pool, and answering it with the whole ledger's pool is itself the bug (#1985). The distinction was maintained only by which level a caller happened to reach for, and by a comment explaining why the `{*}` precondition sits on one and not the other; nothing stopped a filtered replay being handed booking's answer. Callers replaying a filtered stream want `replay_posting`; callers realizing a ledger want `apply`, which applies a whole transaction and runs the precondition first. **Both now refuse an unbooked posting** rather than silently skipping it: a posting whose units are still elided returns the new `BookingError::NotBooked`, where it previously returned success and left the caller with empty balances and no complaint. Booking fills those units in, so a booked ledger cannot reach it — nothing in the workspace suite and none of the 735 compatibility corpus files do (issue #2082, step 1).
- **A file included from more than one place is now reported** — reaching the same file twice in the include graph without forming a cycle (a shared prices or accounts file included from two monthly journals, say) loaded it once and said nothing. Python beancount reports `Duplicate filename parsed` for exactly this and `bean-check` exits 1; rustledger only emitted that diagnostic for a true *cycle*. The file's directives still load exactly once — the report is in addition to loading correctly, not instead of it — but `rledger check` now exits non-zero on a ledger that previously passed. Remove the redundant `include` to fix. The MCP server's `validate_file` reports it too, and no longer inlines such a file twice, which had been silently doubling its amounts (issue #2084 follow-up).
- **STRICT no longer resolves an ambiguous lot match by falling back to FIFO** — when a reduction's cost spec matched several lots that shared a cost number and cost currency, booking drained them oldest-first instead of reporting the ambiguity. The comment justifying that said the user "could not have observed a different outcome" and that beancount does the same; neither was true. Beancount's `booking_method_STRICT` has no fallback, and the outcome is observable because the surviving lot carries its own acquisition date — which drives the short/long split in `report capgains` and per-lot IRR eligibility. Lots that are identical in *every* cost field (number, currency, date and label) are still drained in date order, because beancount's inventory merges those into one position and would never see them as ambiguous. Name the lot (`{74.09 USD, 2022-05-10}`, or a label) or book the account FIFO/HIFO if the choice genuinely does not matter. **`STRICT_WITH_SIZE` is fixed in the same place**: when several lots matched the reduction's size it took whichever was stored first, which is insertion order and only coincidentally date order — a lot with an explicit cost date breaks the coincidence. It now takes the oldest, as beancount does, which changes both the basis realized and the holding period of the lot left standing (issue #2097).
- **Interchangeable lots are stored as one position, regardless of the order they were written** — two lots agreeing on commodity, cost per unit, cost currency, acquisition date and label are indistinguishable in every attribute the model records, yet booking consumed them in acquisition order, so an unrelated lot written between them changed which units were sold. Three purchases on one date at two costs, written in the six possible orders, produced **three** different cost bases where Python beancount produces two: sorting a journal or switching importers could move a reported basis and a realized gain without changing a fact. The tax rule this implements does not reach the distinction either — Treas. Reg. 1.1012-1(j)(3)(i) orders units "in order of time from the earliest DATE" and is silent within one, and IAS 2.23 treats FIFO as a cost-flow assumption over *interchangeable* items. `add` now merges such lots into one position, the way it has always merged cost-less ones, which makes the result independent of write order and removes the last divergence class the differential booking fuzzer reported against beancount: 250/250 seeds now agree with zero divergences, where main reports six. **Cost basis, realized gains, surviving lot dates and `meta.hash` change for any account holding a repeated lot identity within a date**, and a reduction naming an explicit cost may begin or cease to resolve. `add(+10 {cost})` followed by `add(-10 {cost})` therefore nets into one position rather than leaving two lots; booking a sale is unaffected, since that goes through `reduce`. Labels still keep otherwise identical lots apart, which is what they are for. Implemented at parity, marginally faster for having fewer positions to sort (issue #2118, pta-standards RFC on lot consumption ordering).

- **LIFO now takes the FIRST of two same-date lots, not the last** — LIFO walked its candidate list with `.iter().rev()`. That list is sorted `(date, slot)`, so reversing it reversed the *slot* tiebreak along with the sort key, and LIFO consumed the last of two lots sharing a date while FIFO and HIFO consume the first. Python reverses only the primary key: `sorted(key=.., reverse=True)` is stable, so ties keep insertion order in either direction. This was an incomplete migration rather than a decision about LIFO — `order_key` already documented the rule ("Negated rather than reversed so the tuple still sorts ascending and the slot tiebreak keeps its direction"), and #2091 moved HIFO onto it and left LIFO behind. **Any LIFO account holding two lots acquired on the same date at different costs now reports a different cost basis and different realized gains**, and therefore a different `meta.hash`. `Cost` has day resolution, so among same-date lots there is no fact about which was "last in"; this makes LIFO agree with its siblings and with Python rather than recovering a uniquely correct answer. Ledgers that want a specific lot should name it (`{74.09 USD, 2022-05-10}`, or a label). The `reverse` flag is gone from `plan_ordered`/`reduce_ordered` in favor of `LotOrder::DateDescending`, so a reversed tiebreak is no longer expressible (issue #2115, PR #2119).

- **Same-date directives now book in file order** — booking previously floated cost augmentations ahead of the reductions matching against them within a `(date, priority)` group. Python has no such rule (`entry_sortkey` is `(date, type_priority, lineno)`), and the reordering changed which lots a match could see: a sell with an empty cost spec written before a same-date buy became an ambiguous match on a ledger Python accepts (issue #2093). Ledgers that relied on the reorder — a sell written before the same-date transaction that supplies its lot — now report the same error Python does. Writing the two in the order they happen fixes them. `rustledger_core::booking_sort_key` returns `(NaiveDate, DirectivePriority)` instead of `(NaiveDate, DirectivePriority, bool)`, and `Directive::has_cost_reduction` — the source of that third element — is removed with the tiebreak it existed for. Downstream code that destructures the key or calls the predicate needs updating; code that only passes the key to a sort does not (PR #2095).
- **`rustledger-lsp` URI conversion is now fallible and typed** — `uri_to_path` and `path_to_uri` return `Result<AbsPathBuf, PathUriError>` / `Result<Uri, PathUriError>` instead of `Option`. `uri_to_path` also refuses a non-`file:` scheme and any URI whose path segment percent-decodes into path syntax, both of which previously resolved to real filesystem paths. Embedders calling these directly must handle the error; the variants name which step failed (PR #1869).

### Fixed

- **A lot netted to zero no longer counts as a holding, and an undated pool can be sold beside a dated lot** — two ways `book` and `apply` still disagreed after #2368. A short and a buy-back of the same lot in one transaction netted the lot to zero units, and the lot stayed: it still counted as a positive holding, so the next sale read as reducing it and failed with `No matching lot`. That hit plain STRICT and FIFO ledgers that beancount accepts (`-5 X {100}`, `+5 X {100}`, then `-1 X {100}`), and `report balances` listed the empty `0 X {100 USD}` lot. A zero-unit lot now counts for nothing, and a cost-bearing lot netted to zero is removed, as beancount removes it. Separately, a `{*}` merge leaves its pool undated. A later STRICT sale of every lot at that cost booked a per-lot posting for the pool whose missing date also matched the dated lot, and applying it failed with `AmbiguousMatch`. The pool's posting now follows the dated lot at its cost, when it is the only lot left there; sales that already applied keep their posting order. The small-lot agreement property that found both now runs in the suite (issue #2378).
- **BQL `BALANCES` and `account_balance` read a transaction the way booking did** — the query executor replayed each transaction one posting at a time against live state, the pattern #2368 fixed in `apply` and the validator. `BALANCES` then refused ledgers that `check` accepts: `+10 X {100 USD}` then `-20 X {100 USD}` in one transaction failed with `Not enough units` where bean-query answers `-10 X {100.00 USD}`. On an `AVERAGE` account, cost-less units written ahead of a sale joined that sale's pool, so `BALANCES` showed `16 X {50}` where `report balances` shows `6 X {100}` beside `10 X`. The executor now replays through the same walk as `apply` (`BookingEngine::replay_transaction`, and `begin_replay` for per-posting state). A row's `account_balance` is the state that walk reaches over the postings up to and including it. **Values change only where they disagreed with booking**: an `AVERAGE` pool or `{*}` merge that absorbed a purchase from the same transaction, and ledgers the query used to refuse. Over 3000 generated ledgers, every changed `BALANCES` result now matches `report balances` and none did before; FIFO, LIFO and STRICT ledgers the query could already answer are unchanged (issue #2380).
- **A transaction that sells past a lot inside itself is applied the way it was booked** — booking reads every posting against the inventory as it stood before the transaction, plus that transaction's earlier reductions, so a buy never makes a later posting of the same transaction a reduction. Applying the booked result, and the validator's inventory pass, instead added each posting as they reached it. Once a sale ran past the end of a lot and opened a short, a later posting could look like a reduction of that short. `+10 X {100 USD}` then `-20 X {100 USD}` in one transaction, which beancount books as a short of 10, failed `rledger check` with `Not enough units`; holding 2 at 100, `+9 X {101 USD}`, `-2 X {100 USD}`, `-2 X {100 USD}` failed with `No matching lot`. Both passes now walk the transaction as booking does: each reduction applied as it is reached, every augmentation after. **Ledgers that beancount accepts but rledger rejected on this shape now load.** On 2000 generated ledgers of this shape, main disagreed with beancount on 30 and this change on none. Performance is flat on the benchmark ledgers (issue #2368).
- **AVERAGE booking divides by an exactly-summed pool, not by a total that has already been rounded** — the escalation added in #2353 computed the numerator exactly in `BigDecimal` and then divided it by the `total_units` its caller had accumulated with `checked_add`, which reduces the scale to fit rather than failing. On a pool mixing `7.65e-13` with `7.9e13` the exact total needs 39 significant digits, so the argument could not carry it, and the average came out two units in the last place below correct. The denominator is now summed exactly from the same positions the numerator uses, over every position, because a cost-less lot counts toward the pool total the caller summed. The fast path also treats a rounded divisor as grounds to escalate, since its precondition is that the division is the only rounding. Found by #2353's own property test on a fresh seed, which was itself dividing by a third, differently-rounded total: the reference called `...520` correct where the true value is `...518` and the function answered `...516`, so both sides were wrong by two units in the last place in opposite directions. The test now sums its denominator exactly too, and one pool is pinned against a value computed with exact rational arithmetic outside this codebase, because the corrected reference and the escalation path share a formula and can no longer catch a mistake in it alone. All three AVERAGE callers now take their pool total from one helper that reports whether it rounded, where they used to compute it two different ways, one of them with `Decimal`'s panicking `Sum`. No corpus value moves, and none of 8,000 booked sells on each of two synthetic AVERAGE ledgers changes. Measured in instructions on `check --no-cache` over 24,000 transactions with 8,000 AVERAGE reductions: +0.18% on ordinary money and +0.03% on 18-decimal amounts, after an earlier draft that re-summed the pool in the callee cost +0.50% and +1.52% (issue #2363).

- **The valuation plugin reports unusable prices instead of panicking or silently skipping them** — `0 USD @@ 100 EUR` on an account the plugin maps divided the total by the unit count to get a per-unit price, with `rust_decimal`'s bare `Div`, so `rledger check` aborted with `Division by zero` on an ordinary ledger rather than reporting anything. A near-zero valuation price reached the same code the other way, overflowing `cash / price` and aborting with `Division overflowed`. Both are now a plugin error naming the account and pointing at the directive, which is the outcome beancount reaches on the same input (`Error applying plugin`, exit 1) rather than a crash. **The posting is left in its original currency and the error is reported; it is never passed through silently**, which would leave the purchase outside the fund with `rledger check` reporting success. Found while reviewing the exactness change below, and fixed with it because they were the last bare divisions in that function (issue #2360).

- **The valuation plugin's derived values are exact** — `beancount_lazy_plugins.valuation` stored its price as `valuation_amount / unit_balance` in a `Decimal` and then divided cash by that quotient. A derived price usually does not terminate: `1200 / 1125` is `16/15`, of which `Decimal` keeps 28 places, and every unit count and gain taken from it inherited the loss. A 400 USD withdrawal posted `374.9999999` units and a gain of `-25.00000000000000000000000001` where the exact answers, 375 and 25, are both representable; a later sale gave `-125.0000001` and `-274.9999998999999999999999999` against an exact 125 and 275. Buys were affected in the other direction: where the stored quotient overshoots, as `1 / 0.3333...3` does, rounding it up **credited a lot 1e-7 larger than the purchase bought** — 1 USD at a price of `1/3` recorded `3.0000001` units instead of 3. The numerator and denominator are kept now and the division is deferred to `rustledger_booking::prorate`, which multiplies first and escalates to `BigDecimal` when the intermediate product will not fit, so `400 x 1125 / 1200` is exactly 375. The gain is formed as `units x price - units x cost` rather than `(price - cost) x units`: equal in exact arithmetic, but the subtraction-first form collapses both ratios to a `Decimal` before multiplying, which is where the dust came from. Escalating to `BigDecimal` alone would not have fixed this and was ruled out by measurement — from the already-rounded price even exact arithmetic gives `25.0000000000000000000000000117`, so the rounding had to go at its source. Two booked values that used to diverge from beancount now agree: the 2024-03-07 posting price and the 2024-03-05 `SOME_FUND_USD` price directive in `some_fund_example`. **Unit counts, gains and therefore `meta.hash` change for any ledger using this plugin**, and two comparisons against `bean-query` newly diverge (`position-by-date`, `balance-running-assets`) because it still divides by the rounded price; both are pinned with the exact values they should hold. Where a gain genuinely repeats, as `50/1.1` does in `cool_fund_example`, exactness cannot shorten it and rledger reports the correctly-rounded value where bean-query reports its tolerance-grid one (issue #2360).

- **AVERAGE booking's pooled cost is correctly rounded** — the pool's average was `Σ units × cost / Σ units` in `Decimal` throughout, and `checked_mul` rounds a product needing more than 28 decimal places without failing, so a small product lost digits or vanished: 28,146 of 300,000 random pools of comparable small lots came out more than 100 units in the last place from correct, and some booked at a zero cost basis. The sum can round the same way once the products are large, which put another class two units in the last place from correct. Both tiers are now measured for exactness — a product or sum that rounded keeps less than the scale it should — and anything inexact is recomputed in `BigDecimal` and rounded once, the same escalation the balance validator uses for an over-precise residual (#1240). Ordinary pools stay on the `Decimal` path and are unchanged to the last digit. Three cheaper fixes were measured and rejected: every `Decimal`-only form is wrong on one population or the other, because `rust_decimal` keeps 28 decimal places rather than 28 significant digits (a small product loses digits to the floor; a small ratio loses them just the same). This makes `bigdecimal` a dependency of `rustledger-core`, which had avoided one: nothing new enters the workspace, and a `rustledger-parser`-only consumer gains four crates on 65. Measured on `check --no-cache` over 24,000 transactions with 8,000 AVERAGE reductions: -1.2% on 18-decimal amounts, where every reduction escalates, and -1.9% on ordinary money — both inside the run-to-run spread (issue #2353).

- **AVERAGE booking no longer pools small lots at a zero cost** — the pool's average cost was `Σ units × cost / Σ units`, and `checked_mul` rounds a product needing more than 28 decimal places without failing, so a small enough product becomes zero. Two lots of `1e-11` units at `1e-18` and `3e-18` summed to `0` and booked the pool at a zero average cost where it is `2e-18` — a zero cost basis on a real holding, every later sale of it reading as pure gain. That signature (the sum is zero and a product vanished from two nonzero factors) is now recomputed ratio-first; every other pool is computed exactly as before, bit for bit. A broader fix was measured and rejected: ratio-first for every inexact product was worse than the old formula in 70% of random pools, because `rust_decimal` keeps 28 decimal places, not 28 significant digits. That left a sum which loses digits without reaching zero still divided as-is; the entry below finishes it (issue #2351).
- **A compound cost `{a # b}` on a small lot no longer books a zero per-unit cost** — the booker computed the per-unit as `(N·a + b) / N`, where `N·a` is an intermediate product that rounds to zero for a small lot: `1e-11` units at `{1e-18 # 0}` booked a per-unit of `0`. `CostSpec::resolve` and the implicit-price extractor already computed `a + b / N`, the same value with no intermediate product; the booker had drifted from them. All three now call one function, `CostNumber::compound_per_unit`, and a test asserts the booker and `resolve` agree (issue #2351).

- **A tiny `@@` share is no longer booked as zero** — the per-lot share of a total price was computed multiply-then-divide, and `checked_mul` does not fail when a product needs more than 28 decimal places: it rounds, and a small product rounds to zero. `1e-16 × 1e-13 / 1e-10`, a share of `1e-19`, came out `0`, and shares short of zero lost digits in proportion — one differential case was wrong from the 13th significant digit. The product is now used only when it is exact; otherwise the share is formed in `BigDecimal` and rounded once. A randomized test checks every result against an exactly-rounded reference over the whole input range. Average-cost and compound-cost booking have the same shape and are tracked separately (issue #2351) (PR #2350).
- **An uneven `@@` split keeps Python's scale in the capgains exports** — exact shares were divided with `rust_decimal`'s own division, which keeps a non-minimal scale, so a split of `@@ 900` over 1 and 999 units read `0.90` and `899.10` in `rledger report capgains --format csv` and `--format json`, and their sum `900.00`, where Python's `decimal` gives `0.9`, `899.1` and `900.0`. Exact shares now take Python's ideal-exponent scale. TEXT output is unchanged, as is the budget report, both of which round to display precision; the FFI's `session.budget`, which serializes the accrued amount verbatim, changes the same way (`3.50` becomes `3.5`). **The exported strings change for these shares; the values do not.** Two deviations stay, deliberately, and are pinned: an inexact share keeps `rust_decimal`'s precision (up to 29 significant digits where Python rounds to 28), and a share Python would print in exponent form (`6.0E+2`) is written out (`600`) (issue #2349, PR #2350).
- **A `@@` share is computed even when its intermediate product overflows** — a total price of `5e14` over `1e15` of `1e15` units has an ordinary share of `5e14` but a product of `5e29`, so the whole reduction was refused as unrepresentable; before #2344 made the multiplication checked, it panicked. The share is now formed exactly and rounded once. The same computation had been written twice, in the capgains split and the budget accrual, and both now call one function, `rustledger_booking::prorate` (issue #2346, PR #2348).

- **Diagnostic columns count characters, everywhere** — parse errors converted byte offsets with a character-counting helper in `check.rs` while every validate-phase diagnostic used `SourceFile::line_col`, which subtracted byte offsets, so one `rledger check --format json` run carried both conventions and they disagreed by a column per extra byte on any line holding non-ASCII text. `line_col` counts characters now, still finding the line through its cached line-start table, and the duplicate is gone: `line_col_in` is the same rule for callers holding only a `&str`, which is what parse errors have. The two surfaces are pinned to agree at every offset over accented text, an emoji, CRLF and an empty file. WASM and FFI diagnostics move with it, on non-ASCII lines only (issue #2341).
- **Booking errors point at the posting that failed** — `rledger check --format json` reported every `BOOK` diagnostic at line 1, column 1, whatever posting caused it, so an editor consuming the JSON drew the squiggle on the first line of the file. `run_booking` set neither `location` nor `source_span` on the error, though the directive beside it carried both; the text renderer papered over it by appending the date and narration to the message. The location now comes from the posting whose account the failure names — answered in one place by the new `BookingError::account()` and `InterpolationError::account()` — falling back to the directive for failures about the transaction as a whole, such as a balance that does not reach zero. Both `location` and `source_span`/`file_id` are filled, so `file:line:col` consumers and snippet renderers each get what they need (issue #2330).
- **BQL takes `date ± days` and `date - date`** — beanquery accepts an integer day count on either side of `+`, and gives the number of days between two dates for `-`; rledger rejected all three with a type error, offering `date_add(date, n)` and `date + interval(n, 'day')` for the same shifts. `2026-07-01 + 365`, `365 + 2026-07-01`, `2026-07-01 - 365` and `max(date) - min(date)` now answer, so a window written `date < 2026-07-01 + 365` works as typed. The count must be whole, and the rule is deliberately wider than beanquery's in one direction and narrower in another: a whole-valued decimal such as `30.0` is accepted where beanquery refuses every decimal, while a genuine fraction is an error rather than a guess, because a date has day resolution. `date_add` is held to the same rule, which changes what it does with a fraction — see Breaking. `date - date` is computed the way `date_diff` computes it, so the two cannot drift (issue #2324).
- **A `{{total}}` reduction books against the lot its total names** — a sale written with a total cost and no date, such as `-2 CCCC {{100.00 USD}}`, failed with `No matching lot`. After booking matched the lot, the total-cost conversion rewrote the posting's cost with the sale date, so applying it looked for a lot that does not exist. The total was also never compared when matching (`CostSpec::matches` reads a per-unit cost, and a total has none), so a wrong total booked silently whenever that rewrite did not get in the way, including every sale that spans more than one lot (issue #2325). A `{{T}}` reduction now matches on `T / |units|` and keeps the matched lot's cost, as beancount does: a wrong total reports `No matching lot`, dated or not, partial or across lots. Dated `{{T, D}}` sales, which already booked, now carry the matched lot's per-unit cost instead of one rebuilt from the total, so their `meta.hash` changes once. The WASM cache moves (v23, loader unchanged) (PR #2306).
- **A missing `include` is reported at the `include` directive** — the error for an included file that could not be read carried only the target's path, so `rledger check --format json` placed it at line 1 of a file that does not exist, and WASM `BeancountError` had no `file` or `line` for hosts to show. It now points at the `include` line that named the missing file, including when that `include` is itself inside an included file, and the JSON message names the missing target. WASM also sets `phase: "parse"` on the other non-parse load errors now: include cycles, duplicate includes and globs that match nothing. The WASM cache moves (v22, loader unchanged): `Ledger.fromFiles` archives these errors, so a blob written before this change would restore a missing-include error without its location (PR #2322).
- **`rledger extract` flags now override the `importers.toml` entry** — with `--importer` (or `--config` matching a file), the import configuration was built from the entry alone, so `--account`, `--invert-sign`, `--skip-rows`, `--currency`, and every column flag were accepted and silently discarded. An entry with no `account` posted every transaction's account side to `Expenses:Unknown`, and one entry could not be shared across several accounts at the same bank. Precedence is now built-in default, then the entry, then the flag; a flag behaves exactly like writing its key in the entry. The OFX path follows the same order, so `--account` also outranks an OFX entry's account. A `--ledger` profile still outranks both for account and currency. **Behavior change:** a command that passes a flag *and* names an entry disagreeing with it now uses the flag (issue #2304).
- **`rledger format` no longer deletes a note's tags and links** — and neither does the typed-directive emitter behind `rledger add`, `rledger extract` and the FFI `format.entry` endpoints. There are two formatters: `emit_document` in the CST emitter carried a walk that re-emitted the header's `#tag` / `^link` tokens and `emit_note` carried nothing, while `format_note_lines` and `format_document_lines` in `rustledger_core::format` emitted no tags for either directive. So `rledger format` deleted a note's tags, and the typed path deleted a document's as well — which is why `format` looked correct for documents while `add` was not. Same shape as the numberless-posting loss above: the tokens were not reformatted, they were dropped, and what the author wrote could not be recovered from the output. Nothing caught it because the formatter's `IDEMPOTENCE_MATRIX` asserts that formatting twice equals formatting once, and **dropping a note's tags is perfectly idempotent** — stability is not fidelity. The matrix's `note_directive` fixture also carried no tags, so no test in that file could have seen it. Both emitters now share one helper, the fixture carries a tag and a link, and two harnesses compare the parsed model across a round trip — one per emitter, since neither can see the other's output (issue #2184, PR #2192).

- **A blank line before a `note` or `document` no longer eats its tags and links** — a directive node begins with the trivia that precedes it, so when a blank line sat above the directive its first token was a `NEWLINE` and the collection loop broke before reaching anything. That is how ledgers are normally written, so it was the common case rather than a corner: of the three tagged `document` directives in the compatibility corpus, two lost their tags and only the one written directly under another directive kept them. `document` carried this long before `note` had any tags to lose (#2160), and no fixture caught it because every one placed the directive immediately after another. The formatter had already guarded its equivalent walks on a `seen_content` flag; the converter was the outlier. Both parse caches move (loader v32, WASM v16) — the WASM bump was also owed by #2160, which moved the loader version and the pin and left the WASM constant alone, making v15 ambiguous between two `ArchivedNote` shapes (PR #2189).

- **A balance tolerance may follow an arithmetic amount, and a `price` refuses one** — `directive_arithmetic_value` scanned to the first top-level `CURRENCY` and treated everything before it as the amount expression, so with no currency between the amount and the tolerance it swallowed the tolerance: `0.25 + 0.75 ~ 0.01 USD` reached the expression parser as `0.25 + 0.75 ~ 0.01`, which is not arithmetic, and the whole value was reported malformed. Only the currency-less arithmetic form hit it, which is why `100.00 ~ 0.01 USD` and `0.25 + 0.75 USD ~ 0.01 USD` both worked. This is also what made `rledger format` emit a balance that no longer parsed — the formatter emits the single-trailing-currency form, which is beancount's and the one the parser already accepted for a plain number. `~` now ends the expression. Separately, a `price` has no tolerance, so one written there is now diagnosed rather than half-read: `price USD 1.10 ~ 0.01 EUR` previously evaluated to 1.10 and discarded the rest in silence. Both parse caches move (loader v33, WASM v18), because output moves in both directions — a stale blob holds an error where this build produces a balance, and a truncated 1.10 where it produces an error (issue #2191, PR #2195).

- **A `pad` no longer satisfies a balance asserted on the pad's own date** — `Pad` and `Balance` swap `DirectivePriority`, so a same-date balance is now seen before the pad that precedes it in the file and the pad is left with nothing to satisfy, matching beancount. The WASM parse cache moves (v17) although no directive's archived bytes change: `LedgerPayload` stores the output of `process()`, which sorts by `canonical_sort_key`, and that key reads `DirectivePriority` — so the cached *list* is a different list. Pad amounts computed from a stale blob would still come out right, because `process_pads` re-sorts by the same key; what differs is the directive order every order-sensitive consumer reads, which is reason enough for a cache to be stale (issue #2150, PR #2187).

- **`rledger format` no longer deletes a posting's currency, cost or price when it has no units number** — `emit_posting` rendered the amount only when a number was present, and the currency, cost spec and price annotation all sat inside that branch, so a posting without a number lost every one of them. The tokens were not reformatted, they were dropped, and what the author wrote could not be recovered from the output. `Assets:Other USD` is valid beancount that constrains interpolation to USD, so this was data loss on CORRECT input; the malformed shapes matter too, since `format` runs on editor save and mistyping a units number then saving deleted the rest of the line. Found by checking two properties across the 735-file compatibility corpus: formatting is idempotent, and it does not change the set of diagnostics a file produces (issue #2142).


- **`report journal --limit N` no longer reverses the report** — the limit was reached with `.rev().take(n)`, which left the ROWS reversed as well as selecting the last N: the unlimited journal read oldest-first and adding a limit silently flipped it newest-first. `sort_by_key` is stable, so the same reversal also undid the file order of same-date transactions — the order booking itself uses (#2093) — so a limited journal disagreed with the ledger about which of two same-day entries came first. All three output formats were affected; they share the selection. Found by variant analysis from #2115, which was the same `.rev()`-over-a-sorted-list shape in the booking path (issue #2122).

### Performance

- **The exact `@@`-share path costs up to ~5% on 18-decimal ledgers** — the fix for tiny `@@` shares sends any product that is not exact to `BigDecimal`, and an 18-decimal amount times an 18-decimal amount always needs more than 28 places. On a worst-case ledger, where every third transaction is a two-lot `@@` sale of 18-decimal amounts, `rledger check` is 4.8% slower than before, within its run-to-run spread; ledgers with ordinary money are unaffected (measured: −1.8%). It was 13.6% until the `Decimal` to `BigDecimal` conversion stopped going through a string: it now builds `BigDecimal::new(mantissa, scale)` directly, identical in value and scale on 500,010 measured decimals. The precise balance tier (#1240) uses the same conversion; its own speed was not measured (PR #2350).

- **Multi-currency interpolation is deterministic** — residuals were accumulated in a `std::collections::HashMap`, whose `RandomState` is seeded per process, and the multi-currency split fills the original posting from whichever non-zero residual came first. The same ledger therefore emitted its postings in a different currency order from one run to the next: `report balances` on a two-currency absorb produced two distinct outputs across 30 runs before this change and one after. Amounts always agreed, so nothing was wrong with the numbers — but a diff churned, a snapshot could flake, and which posting index carried which currency moved. The order is now the order the transaction introduces each currency. One use site already sorted its keys to dodge this, under a comment saying unsorted order "would produce non-reproducible test output"; that covered one of the three iterations (PR #2105).
- **Interpolation writes in place** — it used to fill a clone of the transaction and hand it back for the caller to assign over the original, so every transaction paid a full clone and the original's drop, 7.7% of a warm `check`, so that a rare failure could be undone. Interpolation touches one or two postings, so those are saved instead. A transaction that fails to book is not discarded — it is set aside and merged back into the ledger — so it must still read as the author wrote it, which is now maintained explicitly and asserted (PR #2105).
- **The source-map line index is built on first use** — every consumer is a diagnostic (`line_col`, `line`, `line_start`, `num_lines`), so a ledger that reports nothing built a `usize`-per-line table and never read it: 6.8M instructions and 320 KB on a 40,000-line ledger. `line_col` also stops locating a line with a linear scan over a sorted array in favor of a binary search, which only one diagnostic never noticed and a file reporting thousands paid for each time (PR #2105).
- **`simple_index` folded into the units cache** — two maps keyed on the same interned currency and always read together, so `add` hashed it three or four times per posting. Beyond the hashing, a stale slot was harmless but a missing one was a wrong answer, so keeping the pair in agreement was a standing obligation at every mutation site (PR #2105).
- **`rledger check` cache-hit path** — the path the nightly benchmark actually measures, since `bench.yml` runs hyperfine with the parse cache enabled and every timed run is therefore a hit that never parses. It had regressed 22% since v0.21.0 (215.7M vs 176.8M instructions on the 10,000-transaction workload) and is now back to parity at 177.3M, and ~20% better in wall clock because most of what was recovered is memory the instruction count does not see. Four changes: the dead `SourceCache`; `CacheEntry::into_load_result` decoding cached source with `from_utf8_lossy(..).into_owned()`, which validates a byte at a time and copies even when every byte was valid, where `DiskFileSystem::read` already used `String::from_utf8` with a lossy fallback (22.8M instructions, 12.9% of the run); a tautological `sum <= Decimal::MAX` after a `checked_add` that returns `None` on overflow by definition, run twice per posting; and interning during rkyv deserialization under a scoped `InternScope` instead of deduplicating with a second whole-directive walk afterwards (PR #2104).
- **Cold `check` is 31% faster than v0.21.0** (797.3M -> 552.4M instructions), mostly the quadratic work in #2056-#2067 plus right-sizing the per-transaction `postings` vector — `Vec`'s first allocation is 4 elements, so a two-posting transaction reserved four slots' worth to hold two, 10,000 separate overshoots on a 10k ledger (PR #2104).
- **PR benchmarks build the allocator the release binaries ship** — `bench-pr.yml` built both sides without `--features mimalloc` while `release-build.yml` ships it, so the job compared two builds nobody installs. Not cosmetic: a string-interning change measured -14% against the system allocator and 0% against mimalloc, because what it recovered was glibc's per-allocation overhead. It was dropped rather than shipped; the job as written would have endorsed it (PR #2104).

- **Source double-allocation removed** — `Arc<str>` for source code instead of clone (Phase 0.1, ~16% faster, 50% less source memory).
- **Profile-Guided Optimization (PGO)** — release binaries built with benchmark profile data (Phase 0.2, ~13% faster).
- **LTO release profiles** — `thin` LTO on `release` (avoids Apple linker crash), `fat` LTO on dedicated `release-linux` and `wasm-release` profiles, with `codegen-units = 1` + `strip` (Phase 0.3).
- **Zero-copy string parsing** — parser returns borrowed `&str`/`Cow<str>` and interns later instead of eager `.to_string()` (Phase 1, ~7% faster).
- **FxHashMap / rustc-hash on hot paths** — non-cryptographic hashing for interned-string/currency keys across core, validate, booking, query, loader; inventory hot path is fxhash-only (Phase 2.4, issue #1237).
- **imbl persistent collections** — `Inventory.positions` uses `imbl::Vector` for O(1) clone via structural sharing, removing quadratic snapshot blow-up (Phase 2.5, issue #1086).
- **Full string interning** — `InternedStr` extended to payee/narration/tags/links on `Transaction` and `Document`; cache re-interning deduplicates 150+ strings/ledger (Phase 3, ~6% faster).
- **Rayon validation parallelization** — parallel transaction interpolation and independent checks, sorting kept sequential (Phase 4, ~5% faster).
- **Parallel query execution** — simple per-posting query evaluation runs via `par_iter()` above a threshold, `DISTINCT` dedup stays sequential (Phase 4.3).
- **parking_lot locks** — faster, smaller, non-poisoning `RwLock`/`Mutex` in query executor and LSP state (Phase 4.4).
- **Binary cache (rkyv)** — zero-copy deserialization cache keyed on BLAKE3 of path+mtime+size, with invalidation and `--no-cache`/`-C` CLI flags; 2.3x faster on cache hit (30ms → 13ms) (Phase 5, issue #939).
- **Logos lexer + structured rowan CST parser** — SIMD-accelerated tokenization and hand-written lossless CST, replacing the Chumsky combinator parser (Phase 6.1).
- **Parser fast paths** — empty-collection avoidance, SIMD escape check, in-parser string interning, hand-rolled Decimal/date parsing, `Cow` strings; 1K txns 1,204μs → 700μs, -42% (Phase 6.3, PR #812).
- **Validation fast paths** — precomputed tolerances, BigDecimal bypass when Decimal residual is zero, alloc-free account-name validation; 1K txns 210μs → 90μs, -57% (Phase 6.4, PR #814).
- **Parallel file loading** — sibling includes read + parsed in parallel via rayon with sequential order-preserving merge (DiskFileSystem only); multi-file ledgers load 2-4x faster (Phase 6.5, PR #813).

**Overall:** ~20x faster validation and ~34x faster balance reports vs Python beancount on 10K-transaction ledgers; ~13ms on cache hit.
